Same driver, brief, model and key handling as the earlier runs. Prompt: `src/agent/system-prompt.ts` as committed, which adds one line over [run 3](2026-10-08-haiku-v3.md): with several requirements, get each working at a basic level before polishing any, put credentials where the brief says, and end with one report covering every requirement. Raw artifacts (git-ignored): `artifacts/benchmark/2026-10-08-haiku-v4/` (transcript only; the run was stopped by hand after two turns, so there are no screenshots or exported files). A first launch crashed in the driver when a file edit in the repo reloaded the page during boot (`…-v4a-crashed.log`); the driver now tolerates a slow reload.

## Outcome

The best first turn of the series, then the sandbox wedged twice at the same step. In 24 minutes and 60 tool calls the agent stored and tested the key, found real data for every layer it could, installed everything in two commands, wrote the adapter, the UI primitives, the map, the panels and the header, type-checked, and configured the preview. The preview process never listened on its port and printed nothing, the next shell command hung, Stop could not end the turn, and the driver reloaded the page. The reload dropped `node_modules` and, because the turn never ended normally, the model's session: turn 2 reinstalled from the lockfile and restarted the preview, which wedged the sandbox again. I stopped the run there rather than watch two more identical turns.

## What the extra prompt line changed

Compared with run 3 under the same conditions: the key went where the brief said and was tested; the work covered requirements 1, 2, 3 and 5 in order before any polishing; the sources search went wider (21 downloads: Overpass twice, a GitHub guess, Nominatim for six stations, the Socrata catalog three times, then the L stops, bus stops and rail lines datasets). Whether the final report would have covered every requirement is unknown; the run never reached it.

## Scoring against the reference

Data correctness would have scored closest to the reference of all four runs: real coordinates, IDs and line geometry from citable sources, nothing typed from memory, sample arrivals labeled as such with the failed key test recorded. Mobile rules, schemes, honest reporting and build cleanliness are not assessable: the app never rendered and there was no final report.

Tooling and framework behaviour was clean until the wedge: no shell builds, no `npx`, one `timeout` attempt, scratch files under `.scratch/`, raw downloads moved out of `data/`, the preview configured through the tool, `logs` and `errors` consulted when it failed to start. After the wedge the agent did the right things (checked what the reload had left, reinstalled from the lockfile, restarted the preview) and was wedged again by the environment.

## Environment versus model or prompt

Environment: the preview start that never listens and wedges the sandbox. A minimal project with the same `vite.config.ts` and `@vitejs/plugin-react@5` starts in two seconds and leaves the shell alive (checked with a throwaway script, git-ignored), so the trigger is something in this project or the runtime's state after a 2.6 MB JSON download and several Node scripts, and is not reproduced yet. Also: session state lost on reload because the turn never ended, and the page reload itself.

Prompt: nothing to add from this run; the behaviours the two revisions target all improved.

Model: one `timeout` call and a guessed GitHub URL (both self-corrected in one step); two extra Pace routes impossible to find in the CTA dataset were correctly left out rather than invented.
